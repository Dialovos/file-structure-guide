# `.gitignore` and keep-files

## TL;DR

`.gitignore` is what you exclude from the repo (build output, caches, secrets, OS junk). `.gitkeep` is the workaround for git's refusal to track empty directories — drop one in, and the directory persists. Both are mandatory hygiene; neither is optional once the repo is more than a toy.

## Principles & why

A repo's tracked content should be exactly what *belongs* there: source, configuration, docs, fixtures. Everything else — `node_modules/` (regenerable), `dist/` (regenerable), `.env` (secret), `.DS_Store` (OS noise) — is either reproducible from source or actively dangerous to commit. The `.gitignore` file is how you say so, and the cost of forgetting is real: leaked secrets, bloated history, merge conflicts in regenerated artifacts.

The other half of the principle is structural. Git intentionally doesn't track empty directories — its model is "track files", and an empty dir is just a file system optimisation. But your *layout* often demands certain dirs exist before files arrive: `data/raw/` for a dataset that hasn't been downloaded, `logs/` for a service that hasn't run, `migrations/` for a feature that hasn't shipped. The fix is a placeholder file. `.gitkeep` is the most common name; `.keep` (Rails) and a real `README.md` are the alternatives.

A subtle point: `.gitkeep` is **not a real git convention**. Git has no opinion on it. The convention is "any single file in the directory makes the directory tracked", and `.gitkeep` is just the most popular naming choice. That's why `.keep` works equally well, and why a one-line `README.md` is often a better choice — it does the same job *and* documents the directory's purpose.

## When to use

**`.gitignore`** — always. There's no project so small it doesn't have build output, OS files, or editor swap files. The minimum viable `.gitignore` covers:

- **Build/output dirs** — `node_modules/`, `dist/`, `build/`, `target/`, `.next/`, `__pycache__/`, `*.egg-info/`.
- **Secrets** — `.env`, `.env.*` (but typically allow `.env.example`), `*.key`, `*.pem`, `credentials.json`.
- **OS junk** — `.DS_Store`, `Thumbs.db`, `desktop.ini`.
- **Editor files** — `.vscode/` (when team-shared, allow specific files like `.vscode/settings.json`), `.idea/`, `*.swp`, `*~`.
- **Logs and temp** — `*.log`, `tmp/`, `coverage/`, `.cache/`.

**`.gitkeep`** — whenever an empty directory is part of the *canonical* layout and must exist before files arrive:

- Data ingestion dirs (`data/raw/`, `data/processed/`, `data/interim/`).
- Log/output dirs that aren't ignored but are empty until the app runs.
- Required-by-tooling dirs (`migrations/`, `seeds/`) before the first migration is written.
- Plugin/extension dirs that are populated by users.

## When NOT to use

- **`.gitignore` for one-off files** — don't `.gitignore` `my-personal-debug.log`. Use a global gitignore (`~/.config/git/ignore`) for personal habits, not the team file.
- **`.gitkeep` in a directory that has real content** — once `data/raw/` has data files, the `.gitkeep` is dead weight. Delete it.
- **`.gitkeep` in directories that get populated by setup** — if your bootstrap script creates `logs/` before the app needs it, you don't need a tracked placeholder.
- **`.gitkeep` to track a *secret*-holding dir.** Empty plus tracked still leaks the *existence* of the path. If a directory's existence is sensitive, don't track it.
- **`.gitkeep` mixed with `.keep`** — pick one across the project. Mixing two names creates the same "which is real" problem the principle is trying to avoid.
- **`.gitkeep` instead of a real `README.md`** — if you have *anything* to say about the dir ("this holds raw downloaded data; never commit files here, see ../scripts/download.sh"), say it in a `README.md`. The README does both jobs.

## Naming rules

1. The file is exactly `.gitignore` — leading dot, lowercase, exact spelling. Git matches this filename literally.
2. Pick one keep-file convention per project: `.gitkeep` (most common), `.keep` (Rails-flavored), or a `README.md` (best when you have anything to say). Don't mix.
3. `.gitignore` patterns are **path-relative**: a `.gitignore` in `src/` only applies to that subtree. Use the root `.gitignore` for project-wide rules.
4. **Anchor patterns** that should be project-root-only: write `/dist/`, not `dist/`. Without the leading slash, the pattern matches `dist/` at any depth.
5. **Negate sparingly**. `*.log` followed by `!important.log` works but reads poorly; prefer narrow positive patterns when you can.
6. Comment every non-obvious pattern. Future-you won't remember why `*.foo` is ignored. `# generated by build.sh — see Makefile target` is a 30-second investment with a 5-year payoff.
7. Order patterns by category with section comments (`# Build output`, `# Secrets`, `# OS files`). Easier to audit.

## Worked example

A data project needs `data/raw/` and `data/processed/` to exist on clone, but their contents must not be committed.

1. In `.gitignore`, ignore the contents but not the directory placeholder:
```
/data/raw/*
/data/processed/*
!/data/raw/.gitkeep
!/data/processed/.gitkeep
```
2. Create the placeholders: `touch data/raw/.gitkeep data/processed/.gitkeep`.
3. Verify what git sees: `git add -n data/` lists only the two `.gitkeep` files.
4. Check that a real file is ignored: `git check-ignore -v data/raw/sample.csv` prints the matching rule.
5. Put a one-line note in `data/README.md` saying where the raw files come from.

Anyone cloning gets the directory skeleton and a documented way to fill it.

## Anti-patterns

- **No `.gitignore` at all.** Symptom: `node_modules/` in the first commit. Bloats history forever.
- **`.gitignore` accidentally ignores its own purpose.** A pattern like `*` at the top of `.gitignore` ignores literally everything; the file works but the rule is wrong. Read it.
- **Committing `.env`.** The single most common security incident. Always ignore `.env*`; allow `.env.example` explicitly with `!.env.example`.
- **`.gitkeep` *and* an `index.md` *and* a `README.md`** all in the same empty dir. Pick one.
- **Filename collision with the surrounding language.** Some Python projects use `.keep`; some use `__init__.py` to mark the dir as a package (which incidentally also makes it tracked). If the dir is also a Python package, prefer `__init__.py` — it does both jobs.
- **Tracking `.gitkeep` in a dir that's also `.gitignore`d.** The two rules collide. Either the dir is meant to be excluded (then don't add a placeholder) or it isn't (remove the ignore).
- **A 5,000-line `.gitignore`** copied from a stale boilerplate. Most lines don't apply; a fresh reader can't tell what's intentional. Trim aggressively.

## Scaling & failure modes

- **Global vs project ignores.** Editor and OS junk (`.DS_Store`, `*.swp`) belongs in the user's global ignore (`core.excludesFile`), not in every repo. Project ignores hold what the project generates.
- **Negation rules are order-sensitive** and can't re-include a file whose parent directory is excluded. Ignore `dir/*`, not `dir/`, when you need exceptions.
- **Already-tracked files** stay tracked after you add them to `.gitignore`; run `git rm --cached`.
- **Monorepos** benefit from a per-package `.gitignore` next to the code it describes, plus a small root file for repo-wide patterns.

## Variants

- **`.gitkeep`** — the most common keep-file name. No special git semantics; it's a community convention.
- **`.keep`** — Rails-flavored shorter form. Same mechanic. Pick this if your team or framework already does.
- **`README.md`** — preferred when you have anything to say about the directory. Two jobs in one file: preserves the dir *and* documents it.
- **`__init__.py`** — Python-specific; marks a directory as a package and incidentally keeps it. If the dir is a Python package, this is the right choice.
- **Modular `.gitignore`** — split rules across files: `.gitignore` at root, `data/.gitignore` for data-specific patterns, `docs/.gitignore` for site-build artifacts. Easier maintenance in monorepos.
- **Generated `.gitignore`** — tools like `gitignore.io` produce a starter `.gitignore` per language/framework. Useful baseline; trim afterward.

## Adoption checklist

- [ ] `git status --ignored` shows only expected ignored paths.
- [ ] Every directory that must exist but starts empty has a `.gitkeep` (or a real README).
- [ ] `.env` is ignored and `.env.example` is tracked.
- [ ] `git check-ignore -v <path>` explains any surprising ignore.

## Real-world projects using this

- **Ruby on Rails** — `.keep` is the canonical Rails convention; `rails new` generates `.keep` files in empty `tmp/`, `log/`, etc.
- **Cookiecutter Data Science** (https://github.com/drivendata/cookiecutter-data-science) — pre-seeded `.gitkeep` in every empty `data/`, `models/`, `references/` directory.
- **Maven** projects — empty `src/main/resources/` and similar conventional dirs; community typically uses `.gitkeep` or a `placeholder` file.
- **GitHub's official `gitignore` repository** (https://github.com/github/gitignore) — canonical per-language `.gitignore` templates; the source of most starter ignores.
- **Create React App / Vite generated repos** — ship a `.gitignore` covering `node_modules/`, `dist/`, `.env*`, `.DS_Store` out of the box.
- **Python's `__init__.py` convention** — every non-namespace package directory contains `__init__.py`; it serves both as a package marker and as the keep-file in otherwise empty package dirs.

## Migration & references

To audit an existing repo for missing `.gitignore` coverage:

```bash
# Show files that probably shouldn't be tracked
git ls-files | grep -E '(\.env$|node_modules/|\.DS_Store|/dist/|/build/|\.log$|__pycache__/)' || echo "clean"
```

If the audit finds something already-committed:

```bash
# Stop tracking but keep the local file
git rm --cached <file>
echo '<file>' >> .gitignore
git commit -m "chore: stop tracking <file>; ignore going forward"
```

Note: `git rm --cached` only removes from future commits. Old history still has the content — for secrets, you need `git filter-repo` (or BFG) and a force push, plus rotating any leaked credentials.

To audit empty directories that should have a keep-file:

```bash
# List dirs that are tracked but contain no files (other than dotfiles)
find . -type d -empty -not -path './.git/*'
```

A canonical starter `.gitignore` (extend with your language/framework):

```gitignore
# Dependencies
node_modules/
vendor/

# Build output
dist/
build/
target/
*.egg-info/

# Secrets — never commit
.env

```
